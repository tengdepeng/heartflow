## 一、现状架构（名义分层）

```
src/
├── App.vue (1305行/33KB — 巨型根组件)
├── main.ts (87行 — 职责清晰，正常)
├── engine/        # 引擎层：ai / rendering / storage(被360文件直连)
├── modules/       # 61个特性模块（对应蓝图房间），每模块含 __tests__
├── stores/        # 14个 Pinia store + index barrel
├── resonance/     # 共鸣协议层（本应只定义接口）
├── components/    # 跨房间通用组件
├── composables/   # 组合式逻辑
├── router/        # 路由
├── types/         # 全局类型
├── utils/         # 工具（含 time.ts 等）
├── views/         # 房间视图（29个 >800行）
├── archive/       # ⚠ 空目录（0文件）
├── benchmark/     # ⚠ 游离工具，未被构建引用
└── nul            # ⚠ Windows NUL 残留垃圾文件
```

该结构**名义上**对应蓝图17 的"七层+贯穿层"（engine=可插拔引擎层、modules=功能插件生态层、resonance=共鸣协议层、stores/components=调度与呈现）。问题是**实质耦合严重偏离了该架构意图**。

## 二、核心问题清单（四类）

### 2.1 模块划分不合理
| 问题 | 证据 | 影响 |
|---|---|---|
| **上帝视图**：13 个视图 >50KB，27 个文件 >800 行 | `KnowledgeTower.vue` 3385行/`GuardRoom.vue` 3362/`Craft.vue` 2941/`Career.vue` 2551/`DailyAnchor.vue` 2549/`EmotionGarden.vue` 2089 等 | 单文件不可维护、难以测试、合并冲突高发 |
| **上帝模块**：业务逻辑堆积在模块文件 | `knowledge/graph-visualization.ts` 2048行、`mirror/personality-model.ts` 1753、`body/health-report.ts` 1530、`timeline/narrative-generator.ts` 1484、`career/career-simulator.ts` 1431 | 同上 |
| **同名领域双份（module + store 冗余）** | `style`(store↔module)、`timer`(store↔crystal+timer module)、`plugin`(store↔module)、`perception`(store↔module) | 边界冗余，状态归属不清，易产生双源真相 |

### 2.2 依赖关系混乱
| 问题 | 证据 | 影响 |
|---|---|---|
| **`engine/storage` 全局直连枢纽** | 被 **360** 个文件 `import { storage } from '../../engine/storage'`（几乎每个模块 index 都直连落库） | 模块绕过 store/resonance 直接共享状态底座，违反分层；storage 改动牵一发动全身 |
| **store → module 反向依赖（下层泄漏）** | 12 处跨 7 个 store：如 `stores/advisor.ts`→`modules/constitution/*`、`stores/config.ts`→`modules/gesture/*`、`stores/timer.ts`→`modules/crystal`、`stores/style.ts`→`modules/style` | store 层本应只持状态，却下沉了模块逻辑，分层倒置 |
| **`resonance/` 混入实现** | 自述"只提供注册表机制"（`resonance/index.ts:3-4`），却含单例注册表（`index.ts:29-41`）+ `implementations/`（具体类）+ `bridges/`（advisor/anchor/emotion/health… 具体桥接） | 违反"共鸣协议层只定接口"的架构约定 |
| **中央 barrel 枢纽** | `modules/index.ts` **432 行** re-export 全部 56 个模块（虽外部 `@/modules` 引用为 0，但隐性将所有模块相互可达） | 全量 re-export 拖慢 tree-shaking，掩盖真实依赖 |
| **模块间单向耦合 10 对** | `canvas→carrier→will`、`cognition→light`、`timeline→anchor`、`timeline→emotion`、`space→customization`、`space→timeline-index`、`canvas→note`、`reward→worklog`、`anchor→goal` | 虽无双向环，但跨房间直接引用内部实现，绕过 resonance 边界 |

**循环依赖现状**：经全仓 grep，**无 store→store、无模块双向环**。真正的"耦合枢纽"是 `engine/storage`（360 直连）与 `modules/index.ts`（432 行 barrel），而非经典双向环。这是本工程依赖问题的特征——**中心辐射式过度耦合，而非网状环**。

### 2.3 命名不规范
| 问题 | 证据 | 影响 |
|---|---|---|
| **TS 类型/接口/枚举前缀纪律缺失** | `I` 前缀仅 20 处 / 导出 interface+type 约 7566 处；`T` 前缀 0；`E` 前缀 0 / 总 enum 33 | 类型与值命名无区分，可读性差，重构时易误用 |
| **同义函数散落** | `formatDate`/`formatTime` 至少 15 处重复 `utils/time.ts`（`body/health-report.ts:219`、`emotion/garden-narrative.ts:267`、`mirror/topic-clustering.ts:714`、`note/markdown-export.ts:384`、`play/data.ts:50`、`seasonal/index.ts:249` 等）；`engine/timer.ts:95` 另有同名 `formatTime`（签名不同） | 行为漂移风险（同样的名字不同实现），重复维护 |
| **相对路径漂移** | 模块内多用 `../../stores/...` 相对路径，几乎无人用 `@/stores` 别名 | 移动文件即断链，重构脆弱 |

> 优点：`.vue` 组件 **100% PascalCase（0 个 kebab-case）**，无中文/空格文件名——此项纪律良好，保持即可。

### 2.4 冗余与死代码
| 项 | 证据 | 处置 |
|---|---|---|
| `src/archive/` 空目录 | `find archive -type f` = 0；全仓无 import 指向 | **删除** |
| `src/nul` 垃圾文件 | 内容为 bash 报错 `dir: cannot access '/s'…`（Windows `NUL` 设备名残留） | **删除**（否则干扰跨平台工具链/构建） |
| `src/benchmark/` 游离工具 | 仅 `benchmark/index.ts`，靠 `npx tsx` 独立运行；全仓无模块 import 指向（命中的 `benchmarkLayouts` 为方法名，无关） | **迁移**至 `scripts/` 或移除 |
| 重复日期格式化 | 见 2.3 | **收口**到 `utils/time.ts` |

## 三、整改方案（分阶段、可验证、不破坏核心功能）

> 设计目标对齐蓝图17 架构意图：保留 `engine / modules(房间) / resonance(协议) / stores / components` 分层，修复对它的偏离。每一步独立 commit，配测试门禁。

### 阶段 0 · 建立防护网（低风险，先做）
- 引入 **ESLint + `@typescript-eslint/naming-convention`**，强制：interface `I` 前缀、type `T` 前缀、enum `E` 前缀；保持 `.vue` PascalCase。
- 引入 **`madge`/`dpdm`** 到 CI，开启 `circular` 检测，作为回归门禁（目标：circular=0）。
- 统一路径别名：将 `../../` 相对引用逐步替换为 `@/` 别名（结合 IDE 批量重构，避免手改断链）。
- **验证**：`eslint .` 通过；`madge --circular src` 返回 0。

### 阶段 1 · 清理死代码与重复（低风险，可立即执行）
- 删除 `src/archive/`、`src/nul`。
- 迁移 `src/benchmark/` → `project/frontend/scripts/benchmark/`（或移除）。
- **收口 `utils/time.ts`**：grep 全仓 `formatDate|formatTime` 的 15+ 处本地副本，统一改为 `import { formatDate, formatTime } from '@/utils/time'`；消除 `engine/timer.ts` 中签名冲突的同名函数（改名 `formatDuration`）。
- **验证**：`vue-tsc --noEmit` 通过；`vitest run` 全绿；`npm run build` 成功；删除后全局 grep 无残留引用。

### 阶段 2 · 收敛依赖枢纽（中风险，需测试护航）
- **`engine/storage` 抽 repository 边界**：新增 `engine/storage/repository.ts`，封装原始 storage API；**禁止模块直接 `import storage` 原始对象**，统一经 repository 或经 resonance「数据引渡」接口访问。分批迁移 360 处（按模块逐个 PR，每 PR 跑全测试）。
- **消除 store→module 的 12 处运行期依赖**：store 仅保留 **type-only import**（编译期类型，运行期不依赖模块逻辑）；把下沉的业务逻辑上移回对应 module / composable。
- **`resonance/` 纯化**：将 `implementations/`、`bridges/` 收敛为"默认实现"迁移至 `engine/` 或 `modules/`，`resonance/` 仅留接口契约与注册表 schema（保留注册表本身——它是协议层职责）。
- **验证**：`madge --circular` 仍 0；`engine/storage` 直连计数从 360 下降；`vue-tsc` + `vitest run` 全绿；Tauri dev 冒烟（核心房间可记录/读取）。

### 阶段 3 · 拆分上帝组件/模块（高风险，按房间逐个）
- 优先级对齐蓝图17 实施顺序：**P0 房间先拆**（镜我/笔记/情绪/长廊），再 P1/P2。
- 拆分策略：视图只保留「编排 + 路由」骨架；业务逻辑下沉到 `composables/<room>/` 与该 room 的 module；大段模板拆为 `components/<room>/` 子组件。
- 清单（Top 视图，按行数）：KnowledgeTower(3385)、GuardRoom(3362)、Craft(2941)、Career(2551)、DailyAnchor(2549)、EmotionGarden(2089)、Rest(1957)、Home(1765)、Bag(1745)、MaterialWorkshop(1673)… 模块侧：knowledge/graph-visualization(2048)、mirror/personality-model(1753)、body/health-report(1530)、timeline/narrative-generator(1484)、career/career-simulator(1431)。
- **验证**：每个房间拆分后该视图行数 < 400；对应单元测试不降反增；`vitest run` 全绿；视觉回归（截图比对）无变化。

### 阶段 4 · 合并冗余同名领域 & 收敛 barrel（中风险）
- 评估 `style / timer / plugin / perception / crystal` 的「module + store 双份」：将 store 降级为该 module 的**状态切片导出**（或合并入 module，store 仅做 Pinia 适配壳）。
- `modules/index.ts`（432 行 barrel）：外部 `@/modules` 引用为 0，确认无用后**删除**；若个别处确需聚合导出，改为「按需子 barrel」或显式 import。
- **验证**：`madge` 无新增环；tree-shaking 体积下降（build 日志比对）；`vitest run` 全绿。

## 五、风险与回滚

- **每个阶段独立 feature 分支 + 独立 commit**；阶段 2/3/4 动用重构，须先跑全测试再合主干。
- **`engine/storage` 收敛**若误伤某房间读取，rollback 该 PR 即可（`engine/storage` 原始 API 未删，仅新增 repository 包装）。

- 不影响核心功能的根保证：**所有阶段均以 `vitest run` 全绿 + `npm run build` 成功 + Tauri dev 核心房间冒烟作为合入门禁**。
